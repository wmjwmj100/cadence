## Trial Review Order
1. 先看 `<trial>/agent/task-meta/instruction.md`，确认题目真实要求。
2. 再看 `<trial>/agent/task-meta/task.toml`，确认 task 名称、类别、难度和超时。
3. 再看 `<trial>/result.json` 与 `<trial>/verifier/reward.txt`，确认是否通过。
4. 如失败，再看 `<trial>/verifier/test-stdout.txt`，定位具体验证失败点。
5. 再看 `<trial>/agent/final.txt`，确认 agent 最终交付了什么。
6. 再看 `<trial>/agent/wecode-home/debug/<root_thread_id>/history.latest.json`，分析真实行为与协作质量。
7. 最后才参考 `<trial>/agent/wecode-home/debug/<root_thread_id>/metadata.json`。

## Reusable Collaboration Findings
- 复杂或不确定任务应采用“最小必要 scoping + 并行推进”：主 lane 可以先沿最可能方案实现，同时派出少量非同质 lane 做验证或补盲，避免先完整探索再实现的串行模式。
- 若 trace 只有 root + 1 个 explorer，且 `spawn_agent -> call -> reply_to_message_id` 闭环完整、黑板被真实复用、也没有空转 `wait` / `read_agent_status` 滥用，则不要把失败主因归到 swarm；更常见的是任务实现失准，只能把协作问题定性为 lane overlap 带来的轻度效率损失。
- 对明确要求输出路径的 artifact 任务，协作框架应把 required artifact 作为收敛对象：先保证“最小可用候选已落到目标路径”，再做可选调参/优化；重跑时 prior missing-artifact 失败应变成控制约束，而不只是背景信息。
- `spawn_agent` 不是协作完成；spawn 后应尽快 `call` 下发具体任务。若 lane 从未被激活，不能把它算作有效协作。
- 若 root 声称采用 explorer/verifier 分工但 trace 只有 `spawn_agent`、没有首个 `call`，应归为 inactive spawn / planned-lane-not-activated；协作框架应在 finalize/continue 前提醒“send call or explicitly cancel/degrade solo”。
- `extract-elf` prompt-only closure guard 重跑显示：提示能促使 root 创建并本地自验 artifact，但不能可靠阻止“spawn verifier 后未 `call` + 空 final / exit 137”；若此类问题复发，应优先上 runtime inactive-spawn finalization guard，而不是继续加长 prompt。
- `extract-elf__ZsKWSJ7` 显示另一类失败：真实 explorer 闭环和 artifact 落盘已发生，但 root 在 900s deadline 前约 41s 才 `call` verifier，未等回包即被 Harbor `AgentTimeoutError` 杀掉；官方 verifier 随后证明脚本存在但 fresh `new.o` 覆盖率 0%。无下载/网络 retry 失败证据，stderr 为空，shell 总耗时约 3s，主要耗时来自模型/推理/协作空档。泛化改进应是 deadline-aware verifier gate、full-requirement-derived/fresh-input verification，而不是继续只补 inactive-spawn prompt。
- `extract-elf__WNos734` 显示完整协作闭环仍可能失败：root 正常 final、explorer/verifier 都被 `call` 并闭环，内部 verifier 在当前 `/app/a.out` 上 verified 682/700=97.43%，但官方 verifier 用 fresh `/app/new.o` 得 0%。泛化改进是 verifier 必须从完整用户契约派生 fresh-instance/generalization probe，并在 `verified` 中标明 `evidence_scope`，当前 fixture-only 不得等同于契约通过。
- `call` 闭环要严格：`message_id` 唯一、`reply_to_message_id` 对齐、`need_reply` 与 obligation 真正形成闭环。
- 对同一 artifact / hash 发起更新版 verifier 请求时，旧 `need_reply` 不能只在语言上判定 stale；必须被回复、显式豁免或由框架支持 supersede/cancel，否则 finalization guard 可能在最终答案后继续阻塞并放大超时风险。
- 接近任务 wall-clock deadline 时，不应新开 `need_reply=true` verifier 请求，除非剩余预算足够等待并整合结果；否则应显式降级为 deferred/cancelled，并基于当前证据收敛。
- verifier 的 `verified` 若附带与硬性验收契约冲突的 caveat，应提升为 blocking caveat / repair_request；不能让“命令可跑但产物/文件契约不满足”的状态通过 final gate。
- verifier 的 `verified` 必须携带覆盖语义：`requirements_covered`、`requirements_uncovered`、`evidence_scope`、artifact hash / staleness；若证据只覆盖 public/eval 子集而用户契约是全分布/全范围，root final gate 应警告或要求显式 override。
- 对服务托管 / localhost handoff 任务，当前会话内 verifier 成功不等于外部 benchmark verifier 可见；必须用 handoff-safe owner（如 supervisor/service manager 或 `setsid`/`os.setsid` 脱离 agent-managed process tree）并验证 PID / session / fresh entrypoint；`nohup`、普通后台任务和 active tool/PTY session 不算持久化。
- 自验命令必须 fail-fast 且隔离源目录；缺少 `set -e` / `&&` 时，前置 `pip install` 失败可能被后续从工作目录直接 `import` 成功掩盖，造成 final 声称验证通过。
- `wait` 只用于“当前确实被回复阻塞”的情况；对于 sidecar / verifier 的“先审一轮、产物好了再叫我”，应直接结束当前 turn，后续由主 lane 重新 `call`。
- verifier 发现 concrete error 时，必须明确失败点、阻塞原因和需要主 lane 先修什么；main 收到 `FAIL` / `ERROR` / `STALE` / `BLOCKER` 时，应优先修复并重新验证。
- verifier 做完 baseline review 但暂时没有可验 artifact 时，应返回当前结论并结束 turn，不应为了“以后复核”而 `wait`。
- reviewer / verifier 不能只重复静态复查同一文件；若问题可能出在 verifier-facing 接口、运行参数或产物契约，必须检查真实调用面。
- 协调者不能空转；若 spawn 了 `coordinator`，必须尽快通过 `call` 指定要监控的 agent、冲突点和协调产出。
- 声称“看过状态 / 用过黑板”必须有真实 `read_agent_status`、`call` 或黑板利用痕迹；不能只在语言层假装协作。
- 子 agent 应继承主线 sandbox；verifier 不应被静默降成只读，否则会破坏黑板写入和真实执行能力。
- 子 agent 的名称应在首轮上下文就稳定可见，避免黑板或 trace 中出现 `unnamed-agent` 干扰协作判断。
- read-only explorer / scout 在完成原始 `need_reply` 并通过 `reply_to_message_id` 回包后，默认应结束当前 turn；只有发现新 blocker、主 lane 显式要求 follow-up，或能提供严格新增的高价值证据时才继续运行或再次 `call`。
- read-only explorer / scout 若先发现足以改变主 lane 方向的核心结论，应优先发送短 `INTERIM` / partial `call` 或写入黑板，再继续完整报告；避免高价值发现等到长报告末尾才释放。
- 小型单文件任务若 root 明确选择 solo，框架不应强行 spawn；但 final 前必须从用户契约派生一组 verifier-facing 边界自验，尤其是取消、清理、并发、持久化等语义任务，避免只测 happy path 后误收敛。
- 对必须写入外部 artifact 的 TB2 任务，若 root 已形成中等置信候选，应优先早落盘并后续修正；不要把唯一写文件动作推迟到长推理或最终图像/OCR确认之后，否则模型/API `stream_start_timeout` 会把“接近完成”变成空产物。
