## Context

The current debugging surface is fragmented across multiple mechanisms:

- `core/src/message_history.rs` stores cross-session plain text entries, but does not preserve full role-typed multi-agent turns.
- `core/src/model_io_recorder.rs` records model I/O traces per thread, but it is thread-local and append-oriented rather than a canonical task-level snapshot.
- `AgentWorkSummaryEvent` in `protocol/src/protocol.rs` carries only `{thread_id, agent_name, summary}` and omits required role-complete payloads and explicit per-message timestamps.
- Multi-agent collaboration already has agent-name registration (`core/src/agent/guards.rs`) plus dispatcher/runtime paths (`core/src/swarm/dispatcher_runtime.rs`), but there is no single unified history that merges primary agent, spawned sub-agents, and global coordinator/dispatcher into one ordered view.

This change is cross-cutting (core runtime, protocol, storage, and UI): it introduces a canonical debug history model that is rewritten on each update and rendered as a multi-lane collaboration timeline.

## Goals / Non-Goals

**Goals:**

- Persist one canonical long history per task/conversation that contains all relevant roles: `system`, `developer`, `user`, `assistant`, `tool`.
- Include all agent participants in that history: primary user-facing agent, spawned sub-agents, and global coordinator/dispatcher agent.
- Record timestamps with second-level precision for every logged item and preserve deterministic total ordering.
- Use overwrite-on-update semantics for the canonical history file so each update replaces prior snapshot content.
- Organize logs under a dedicated folder per conversation/task.
- Expose a frontend collaboration view that displays agents by name (not ID), with clear side-by-side lanes (for 3 agents: left/center/right).

**Non-Goals:**

- Replacing existing rollout persistence formats used for resume/fork behavior.
- Introducing long-term cross-conversation analytics or external log shipping in this iteration.
- Guaranteeing millisecond-level causal ordering in UI (seconds + monotonic sequence are sufficient).
- Reworking collaboration tool semantics (`call`, `wait`, `remind`) beyond what is needed for observability.

## Decisions

### 1. Introduce a canonical debug trace model with explicit role, agent identity, and timestamp fields

Add a new internal trace entry schema (runtime + serialized JSON) with at least:

- `conversation_id`
- `entry_seq` (monotonic per conversation)
- `timestamp_unix_sec` and `timestamp_rfc3339_sec`
- `agent_thread_id`
- `agent_name` (display name)
- `agent_kind` (`primary`, `subagent`, `coordinator`)
- `role` (`system`, `developer`, `user`, `assistant`, `tool`)
- `content` (text/object payload)
- `source_event` (origin marker, e.g. turn input, tool begin/end, collab event)

Why:

- Existing `AgentWorkSummaryEvent` is too narrow to satisfy complete role-level debugging.
- Role-normalized entries let UI and storage stay stable even when event sources differ.

Alternatives considered:

- Extending only `AgentWorkSummaryEvent`: rejected because it cannot represent full conversation item shapes cleanly.
- Keeping separate per-agent logs without canonical merge: rejected because user needs one task-level long history.

### 2. Build a single conversation-scoped aggregator that merges all agent streams deterministically

Create a runtime aggregator keyed by root conversation id. Every instrumented source appends normalized entries through one async writer queue.

Ordering policy:

- Primary sort: `timestamp_unix_sec`
- Tie-break: `entry_seq` generated by aggregator

Why:

- Multiple threads (primary + sub-agents + dispatcher) emit concurrently.
- Deterministic merge order is required for reproducible replay and UI rendering.

Alternatives considered:

- Per-thread merge on read: rejected (higher read complexity and nondeterministic ordering under race conditions).
- Lock-free file appends only: rejected (cannot provide overwrite-snapshot semantics directly).

### 3. Use snapshot-overwrite persistence with atomic replace for canonical history

For each conversation, store debug artifacts under:

- `<codex_home>/debug/conversations/<conversation_id>/metadata.json`
- `<codex_home>/debug/conversations/<conversation_id>/history.latest.json` (canonical snapshot, overwritten each update)

Write strategy:

1. Serialize full canonical snapshot.
2. Write to temp file in same directory.
3. Atomic rename/replace to `history.latest.json`.

Why:

- Matches requirement: each update should cover/replace previous history state.
- Atomic replace prevents partially written snapshots.

Alternatives considered:

- Append-only `jsonl` as primary artifact: rejected (does not satisfy overwrite requirement).
- DB-only storage: rejected for first iteration (adds operational complexity without UI benefit).

### 4. Capture role-complete entries at existing authoritative hooks

Capture points:

- Turn input assembly path for `system`/`developer`/`user` contributions.
- Model output streaming path for `assistant` items.
- Tool registry/handler boundaries for `tool` invocation and output entries.
- Collaboration lifecycle events (`spawn`, `interaction`, `wait`, `remind`) for cross-agent context.
- Dispatcher/runtime hooks for global coordinator messages.

Why:

- These paths already normalize protocol payloads and are the most reliable source of truth.
- Avoids heuristic reconstruction from partial UI events.

Alternatives considered:

- Capturing from UI notifications only: rejected (missing internal role/tool details).
- Capturing only from rollout snapshots: rejected (too coarse, not incremental enough).

### 5. Resolve and persist human-readable agent names as first-class identifiers

Name strategy:

- Prefer registered display names from `AgentControl`/guards.
- Fallback to reserved known names for primary/coordinator roles.
- Final fallback: thread id string.

Persist both `agent_name` and `agent_thread_id` in each entry.

Why:

- UI must display names rather than IDs while keeping stable technical identity for joins.

Alternatives considered:

- Name-only storage: rejected (breaks reconciliation when names collide or change).
- ID-only storage: rejected (violates UX requirement).

### 6. Provide lane-oriented frontend rendering with deterministic placement rules

Expose a debug-trace snapshot endpoint/notification and render lanes by `agent_name`.

Lane placement:

- 1 agent: single center lane.
- 2 agents: left/right.
- 3 agents: left/center/right (primary agent pinned center).
- 4+ agents: stable lane order with horizontal scroll; primary remains centered when possible.

Each entry row shows:

- `[HH:MM:SS]` timestamp
- role badge
- agent name
- content

Why:

- Gives clear visibility into collaboration and causality across agents.

Alternatives considered:

- Single mixed feed only: rejected (hard to inspect collaboration boundaries).
- Lane by thread id: rejected (poor readability for humans).

## Risks / Trade-offs

- [Risk] Rewriting full snapshot on every update can increase I/O for long sessions. -> Mitigation: debounce writes (short interval), keep in-memory latest state, and enforce configurable max snapshot size.
- [Risk] Same-second events from different agents can appear ambiguous. -> Mitigation: include monotonic `entry_seq` and use it as tie-break in UI.
- [Risk] New debug data may include sensitive user/tool content. -> Mitigation: gate behind debug feature flag, document retention, and add optional redaction hooks.
- [Risk] Name changes/collisions may confuse historical lanes. -> Mitigation: persist both `agent_name` and `agent_thread_id`, plus lane metadata in `metadata.json`.
- [Risk] Protocol/UI compatibility drift across clients. -> Mitigation: version the debug trace payload schema and maintain backward-compatible fields.

## Migration Plan

1. Define and version the debug trace schema (runtime struct + serialized JSON contract).
2. Implement conversation-scoped aggregator and atomic snapshot writer under per-conversation folders.
3. Instrument role-complete capture points (input, assistant output, tool events, collaboration events, dispatcher events).
4. Extend protocol/app-server mapping to expose trace snapshots with agent display names.
5. Implement frontend lane timeline rendering and lane placement rules.
6. Add tests:
   - ordering and tie-break determinism
   - overwrite-on-update semantics
   - per-conversation folder layout
   - agent-name rendering and 3-lane layout behavior

Rollback:

- Disable the feature flag to stop writing/serving new debug trace snapshots.
- Existing runtime behavior and collaboration tooling continue unchanged.

## Open Questions

- Should reasoning raw-content events be included by default, or guarded behind a stricter debug flag?
- What is the default maximum snapshot size before truncation/compaction is applied?
- Should frontend auto-refresh push every snapshot update, or poll at a fixed interval?
- Should coordinator/orchestrator lane naming be fixed (`dispatcher`/`orchestrator`) or configurable per collaboration mode?
